# TestAS Simulator

A browser-based practice and exam simulator for all three task types of the digital TestAS core module (*Kernmodul*):

- **Figurale Sequenzen**: a sequence of 4×4 matrices; pick the 5th and 6th matrix from 3 options each (rules: movement, rotation, colour change; bouncing, outer ring, 2×2 block, x+1 step)
- **Mathematische Gleichungen**: systems of equations, every letter has a value from 1–20, exactly one solution
- **Lateinische Quadrate**: a 5×5 Latin square (A–E); work out the letter that belongs in the `?` cell

Tasks are generated by the program itself at three difficulty levels (*niedrig / mittel / hoch*), so there is a practically unlimited supply of different tasks. No build step, no framework: plain HTML + JavaScript. The server is optional.

> **Unofficial practice project.** It is not affiliated with g.a.s.t. or the TestDaF-Institut. It contains no original exam tasks; it only follows the format of the task types.

## Interface

A simple, flat look: no gradients, no large headings, light theme and dark theme (via `prefers-color-scheme: dark`). On the start page, *Prüfung* and *Üben* sit side by side, with the three task types and the results list below. Colours can be changed through the CSS variables at the top of `style.css` (`--accent`, `--bg`, …). During an exam, navigation, login and footer are hidden. The "unofficial" notice appears only in the footer.

## Modes

| Mode | Description |
|---|---|
| **Prüfungsmodus** (exam) | Like the real exam: 20 tasks per type, 25 minutes, feedback only at the end. You can run all three subtests one after another, or just one. Countdown timer, automatic submission, task navigation, flagging, keyboard shortcuts. |
| **Übungsmodus** (practice) | Unlimited tasks, instant feedback and solution, no time limit, selectable difficulty. |

At the end of an exam you get the result broken down by difficulty level, plus a task-by-task review with the solution. Results are kept in the browser's `localStorage`. The exam's seed is shown with the result; the same seed reproduces the same set of tasks.

**Keyboard shortcuts in exam mode:** `←` `→` to navigate; `A`–`E` for Latin squares; `1`–`3` (image 1) and `4`–`6` (image 2) to select the answer for figural sequences; `Enter` = next task in equations.

## Running locally

```bash
npm install            # once: better-auth + better-sqlite3
npm start              # http://localhost:8080 – static files + login + results sync
npm run start:static   # static server only, no dependencies or accounts
npm test               # generator tests (Node 20+)
```

`index.html` loads ES modules, so it does not work when opened from `file://`.

## Accounts (Better Auth)

Login is built on [Better Auth](https://www.better-auth.com/) (email + password, SQLite database in the `data/` folder). With an account, results are also stored on the server, so the same history shows up on every device. On login, the local and server-side lists are merged; on logout, the local copy is deleted.

- `server/auth.js`: Better Auth configuration + history table
- `server/index.js`: static files, `/api/auth/*`, `/api/history`
- `src/auth.js`: client (plain `fetch`, no build)

**Environment variables:**

| Variable | Purpose |
|---|---|
| `BETTER_AUTH_SECRET` | Required in production; a long random string |
| `BETTER_AUTH_URL` | The public URL |
| `DB_PATH` | Database location |
| `PORT` | Server port |
| `ADMIN_EMAILS` | Admin addresses (see *Study groups* below) |

Better Auth's tables are created automatically at startup. If that fails, run `npm run auth:migrate` (= `npx auth@latest migrate --config server/auth.js -y`) and restart the server.

If the site runs on a static host (e.g. GitHub Pages), there is no auth server: the onboarding page explains that registration is unavailable and the signed-in platform stays hidden. Accounts require a host that runs Node (Render, Railway, Fly.io, your own VPS, …).

After signing in, use the **Prüfung**, **Üben**, and **Verlauf** navigation links to open each platform section as its own page. The profile avatar at the right opens **Kontoinformationen** and **Einstellungen**. Settings include display-name and password updates, sign-out, and permanent account deletion; the email address can be changed when email sending is configured (a confirmation link goes to the new address; it only takes effect after the click), otherwise it is read-only.

## Integrity of results and admin access

- **Exam results are recomputed on the server.** The client sends its answers; the server rebuilds the tasks from seed + task count + difficulty (the generators in `src/` are plain ES modules and run in Node) and counts the correct answers itself, so a claimed score is ignored. Exam entries without valid details, or whose solutions do not match, are stored (they stay in the user's own history) but are **not counted in group tests** (`history.verified = 0`). Group tests also only count results with the test's own task count and difficulty. Rows that existed before this check stay valid. Limits: someone who generates the tasks locally can still know the answers, and time and timestamps are reported by the client. Only up to 6 exam entries per request are recomputed (CPU).
- **Admin needs a verified email address** (`ADMIN_EMAILS` + confirmed address). Without a working mail setup, email/password accounts are therefore never admin – sign in with GitHub (its addresses are verified) or configure email.

## Interrupted exams

A running exam is saved in the browser (answers, flags, position, start time of each subtest). If the page is reloaded, the tab is closed or the browser crashes, the exam is restored on the next visit: while time is left it continues with the remaining time; if the time ran out in the meantime, the subtest is submitted automatically with the answers given so far (time = full limit), evaluated and saved to the history – as if the page had stayed open. Subtests that were never started are not counted; after a pause of more than 6 hours they are not offered any more. The state is cleared on sign-out.

## Result details in *Verlauf*

Results saved from now on carry the answers per task. In **Verlauf**, a *Details* button opens the full review: every task with your answer, the correct answer and the explanation, with an optional filter for wrong/unanswered tasks. Exam tasks are rebuilt from seed + task count + difficulty; practice tasks get their own seed. The stored correct answer is compared with the rebuilt task, so if the generators change later the task is simply not shown (answer and solution remain visible). Older results have no details. The server stores them in a new `detail` column of `history` (validated, max. 100 tasks, ≤ 12 kB per entry).

## Study groups and admin view (*Lerngruppen*)

Any signed-in user can create a group; participants join with a code, and the group creator can see the members' results. Admins retain access to all groups.


**Workflow:**

The *Lerngruppen* area is its own sub-page (`gruppen.html`, also reachable as `/gruppen`): the overview is at `#`, a group's page at `#<group id>`.

1. **Signed-in user** → Lerngruppen → New group → enter a name; the join code (`XXXX-XXXX`) is assigned automatically.
2. **Participants:** sign in → Lerngruppen → enter the code → read the notice, consent → Join. Leaving is possible at any time (the group creator or an admin can also remove members).
3. **Group creator** → Lerngruppen → Your groups → Statistics: a table with exams/practice sessions, average per subtest, last activity and trend. Clicking a name shows that member's history (chart + all results). Two CSV exports are available (overview, all individual results; semicolon-separated, decimal comma, UTF-8, opens directly in Excel). Admins can view and manage all groups.

4. **Scheduled tests:** on a group's page the creator plans a test (title, scope = full core module or a single subtest, minutes per subtest, start time). The server picks a random seed. Until the start time, members only see title and time – the seed (= the tasks) is withheld by the API; afterwards a *Test starten* button opens the exam with exactly that seed and time limit. Per subtest the member's first exam attempt after the start time counts; the creator sees who has finished and each member's score and time. The creator can also set an optional **end time** (results saved after it no longer count; members get a warning before starting too late), **edit** a test (title, minutes, end time any time; task count, difficulty and start time only while there are no results) and download the results of a test as **CSV** (name, subtests, score, time, per-subtest details). Deleting a test does not delete members' history entries.

Admins also have a **System overview** with all registered users, usage totals, overall exam/practice performance, and per-user history. **Einstellungen** lets signed-in users change their display name or password; changing the email address needs email sending (see above).

**Privacy:** explicit consent is required when joining (the server enforces it). The group creator and admins can see a member's name, email and all stored results, including earlier ones. Only results saved while logged in exist on the server; anyone who has not joined is invisible to the group creator. For minors, obtain parental consent where required (GDPR Art. 8; the age threshold in Hungary is 16).

**Technical notes:** three new tables, `study_groups`, `study_group_members` and `group_tests`, are created at startup (Postgres and SQLite). The logic lives in `server/groups.js` (API) and `server/stats.js` (statistics, CSV, codes; tested in `test/groups.test.js`), and the UI in `src/admin.js`. Wrong codes are rate-limited (8 per 15 minutes per user). Trend = the last *k* results compared with the *k* before them (k ≤ 3, from 4 results onwards); a change of ±3 percentage points or more counts as rising/falling. Results currently store only the score per subtest, not a breakdown by difficulty.


## Safe Exam Browser (SEB)

The simulator can also be used inside SEB to practise the exam environment:

1. Install [Safe Exam Browser](https://safeexambrowser.org) and the SEB Configuration Tool.
2. In the configuration, set the Start URL to your GitHub Pages address (or `http://localhost:8080` if you run it locally).
3. Set the restrictions you want (quit password, blocked keys, URL filter, etc.) and save it as a `.seb` file; opening that file starts the simulation.
4. When the page runs inside SEB, a "Safe Exam Browser erkannt" badge appears on the start page.

A browser cannot prevent note-taking; you have to follow the "no notes" rule yourself (like the real exam, the simulator offers no way to take notes).

## How are good tasks guaranteed?

- **Figurale Sequenzen:** from the 4 visible matrices, the generator tries every possible rule (movement: row/column/diagonal with bouncing, outer ring, 2×2 block, x+1 step; rotation; colour cycle) and accepts a task only if all matching rules predict the same 5th and 6th matrix. Wrong answers are "plausible" corruptions of 1–2 figures of the correct matrix (a different step along the path, wrong rotation, wrong colour); figures never overlap. In the solution view, the rules are also explained in German.
- **Gleichungen:** the generator keeps adding equations for the hidden solution until only a single combination of values in the range 1–20 remains; the tests verify this with an exhaustive search.
- **Quadrate:** the grid is built so that the `?` cell can be obtained purely through "only one possible letter / only one possible position" deductions. Difficulty is determined by the number of deduction rounds required (niedrig = 1, mittel = 2, hoch ≥ 3) and the number of filled cells.

## E-Mails (Brevo)

Optional: With a [Brevo](https://www.brevo.com) account (free plan: 300 e-mails/day) the server sends

- a **confirmation link** after registration (the account can only be used once the address is confirmed; existing accounts get a new link when they next try to sign in),
- a **password-reset link** ("Passwort vergessen?", valid for one hour),
- an optional **notification when a group test is planned** (opt-in per user under *Kontoeinstellungen*, off by default).

Set `BREVO_API_KEY`, `MAIL_FROM` (a sender verified in Brevo) and optionally `MAIL_FROM_NAME` (see `.env.example`). The API is used over HTTPS, not SMTP, because Render's free plan blocks outgoing SMTP ports. **Without these variables nothing is sent and e-mail confirmation is not required**, so nobody gets locked out. Code: `server/mail.js`; the reset page is `passwort.html`.
